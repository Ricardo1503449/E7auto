## Coordinate rules

- All ROIs and input points in YAML use physical pixels relative to the `2322 x 1306` baseline client, never desktop coordinates or DPI-scaled logical coordinates.
- The baseline is established once during calibration and remains the only template/coordinate space. Runtime validates the game monitor's current effective desktop mode against its full Win32 monitor rectangle. Only current mode `3120 x 2080` requests the exact baseline client; other supported modes use 60% of full monitor width with fixed aspect ratio and a DPI-aware complete-outer-window height cap.
- Non-reference recognition maps and normalizes each requested ROI in memory; points and recognized anchors are transformed only before input. Runtime never adopts the actual size as a new calibration baseline and never recalibrates after a monitor/mode/DPI change.
- Keep ROIs tight enough to avoid similar icons but large enough for normal UI animation.
- Overlay position calibration is recorded in `assets/templates/overlay_position_calibration_manifest.yaml`; it sent no game input.

## Live commissioning sequence

Live testing requires a new, explicit user authorization. Start with source-only window lookup/display-mode/DPI/target-size verification and no input. Validate the exact reference mode first, then at least one supported secondary resolution (including ROI recognition and mapped cursor positions) before enabling clicks. Start the source validator through Windows `RunAs` and confirm it reports administrator elevation before accepting any input result. Then run in-memory recognition with input disabled, followed by a dedicated no-purchase navigation test. That test must validate the one-way top-to-bottom scroll and consecutive-identical top/bottom viewport results. Real clicks must remain disabled until all recognition checks pass. Never test with a real payment flow.
