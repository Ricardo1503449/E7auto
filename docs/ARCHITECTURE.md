# Architecture

## Source organization

`app.py` starts the application. `ui/main_window.py`, `ui/overlay.py`, `ui/pages/`,
`ui/widgets.py`, and `ui/window_chrome.py` own the Qt presentation. `ui/worker.py`
assembles production services and retains the worker-local WGC import.

`automation/session.py` owns each run's lifecycle; `automation/engine.py` coordinates
the business flow. `automation/stop_control.py` owns the shared stop/input lock,
and `automation/snapshots.py` publishes immutable snapshots. `automation/scrolling.py`
accepts narrow callbacks for guarded input, capture, active time, vision and logging;
it does not access engine internals. Progress metrics survive a failed scroll so the
engine can still emit its final performance record.

`ports.py` defines service contracts, including `GameVision`; `vision_types.py`
defines their recognition results. `vision.py` implements recognition and re-exports
the existing result names for import compatibility. Public UI and automation entry
points are retained by their package `__init__.py` files. See [development](DEVELOPMENT.md)
for script locations, focused testing, and planning-file recovery.

## Data and threads

- The Qt main thread owns `MainWindow` and `StatsOverlay` only.
- `AutomationWorker` runs the session on a `QThread` and publishes frozen `RuntimeSnapshot` objects through Qt signals.
- `SnapshotPublisher` is the single counter source and emits the final snapshot once. Later mutation attempts are ignored.
- Overlay activity is snapshot state rather than widget inference: startup publishes `已启动`, confirmed shop entry publishes `刷新ing...`, strategy main-screen recovery publishes `转运ing...`, and finalization publishes `已停止`. The static hotkey hint contains only F5. The overlay is always mouse-interactive and draggable; releasing a drag persists the position. Its top-left `收起` control switches to a draggable circular Logo view, and a click without dragging restores the full panel. Every run starts in the full-panel state. Only a final snapshot exposes the top-right close button so the user can hide the overlay without exiting the application. Starting another run hides the close button and shows the full overlay again.
- `StopController` uses the same lock for F5 requests and input dispatch. Inputs already dispatched cannot be retracted; after F5 wins the lock, no new input callback can begin.

## Fail-closed flow

1. Main-thread configuration validation occurs before any worker or hotkey is created.
2. Because the observed game process runs at High integrity, the production process must also be genuinely Windows-elevated. The standalone executable embeds a `requireAdministrator` manifest; rejecting UAC prevents startup. Unsandboxed execution without UAC elevation is not equivalent.
3. The worker registers bare F5 before locating or manipulating the game window.
4. The overlay remains directly draggable without pausing automation. Moving it does not alter the WGC game-window capture target or window-message input path. Because WGC captures the designated game window rather than the desktop composition, the overlay does not use display-affinity capture exclusion.
5. The game window must be unique. Before any restore/resize, the window monitor's full `Monitor` rectangle must agree with `EnumDisplaySettings(..., ENUM_CURRENT_SETTINGS)` and meet the configured `2560 x 1440` minimum. A restored background window is left inactive; a minimized window is restored with `SW_SHOWNOACTIVATE` and bounded state polling. Startup never requires or requests foreground ownership. The exact `3120 x 2080` reference mode requests the calibrated `2322 x 1306` client; every other supported mode starts at 60% of full monitor width with the same aspect ratio and is uniformly reduced if its DPI-adjusted complete outer window would exceed monitor height.
6. Every capture/input safety point verifies that the window still exists, is not minimized, has the exact process identity and prepared client rectangle, and remains on the same monitor/mode/DPI. Foreground state is not a production gate; any monitor, mode, geometry, DPI, process, or client change terminates without live resize/recalibration.
7. Entry clicks occur only after stable template evidence. Every click/wheel dispatch rechecks the window under the input lock, maps the baseline point to client coordinates, posts the corresponding window message, and logs success only after the platform call returns. Inventory navigation sends six `-120` messages `10 ms` apart (`scroll.interval_ms`) after the top viewport is exhausted. The five configured inter-message sleeps total `50 ms`, down from `500 ms`; this saves `450 ms` of requested sleep per downward navigation, not a measured 90% reduction in total runtime. Individual dispatches do not await game-side processing. Post-wheel settling starts sampling after `100 ms`, checks downsampled pairwise motion every `100 ms`, requires two consecutive observations within `1 px` with phase response at least `0.80`, and fails closed at the configured `800 ms` maximum. A stable candidate must also pass the calibrated full-resolution total translation/change gate before bottom scanning; stale visually stable frames do not end settling. The last three temporally separated settle frames then seed bottom recognition; an identical three-frame key completes immediately, while a mismatch retains its longest stable suffix and captures only the missing frames. Navigation does not depend on fixed top/bottom anchors.
8. Main-screen detection is defined solely by stable recognition of the shop-entry icon. Its alpha-masked template excludes user-dependent wallpaper; no whole-main-screen template is used. After an entry click, the engine waits for stable shop-refresh recognition. On timeout it jointly checks the shop refresh control and main-screen entry icon; only a stable main-screen result permits another entry click, and the bounded sequence stops after three attempts. Strategy-driven exit first requires stable recognition of the calibrated shop-exit control, clicks its calibrated center once, and then requires stable main-screen icon recognition before any wait or re-entry. Normal completion (`budget_complete` or `refresh_strategy_exhausted`) performs the same guarded shop exit and main-screen confirmation before the final stopped snapshot is published; abnormal and manual stops do not add a new exit click.

## Inventory algorithm

Each refreshed inventory is processed as `stable top loop -> one downward scroll -> stable bottom loop`. The reference display path passes the captured ndarray through unchanged. On non-reference displays, one frame wrapper maps each requested baseline ROI to the actual client, crops first, resizes it back to the exact baseline ROI size once, and caches that result for all detectors using the same ROI; full frames and template assets are never rescaled. Recognition anchors remain in baseline coordinates and are mapped only immediately before guarded input. Inventory vision then compares only this run's enabled available/purchased target states. Slots already completed in the current inventory are excluded before template matching; each remaining slot keeps only the highest-confidence classification. Repeated purchased-state skips are emitted once as a per-scan summary rather than synchronously once per frame. A scan result becomes actionable only after the same ordered `(slot_id, target_id)` list appears for the configured consecutive-frame count; the empty result uses the same rule. Mandatory targets are always enabled, and Friendship Points are matched only for runs whose checkbox was selected.

Adaptive scroll logging is aggregate rather than per-sample event spam. `scroll_settle_trace` records sample times, pairwise shifts/responses/change fractions, consecutive-stability counts, actual settle duration, and early-exit saving. `scroll_verified` retains the full-resolution before-to-final displacement evidence and adds the settle summary. `performance_stage stage=scroll_to_bottom` reports both the configured maximum and actual settle time. The following bottom `inventory_scan` stage reports `cache_outcome`, cached-frame availability/usage, cached stable suffix, fresh-frame count, and residual cache wait so live evidence can distinguish a direct hit from bounded fallback.

Within either viewport, the first enabled match in calibrated slot order is purchased. An explicit success increments its target count, records that slot as completed for the current inventory, discards the old scan list, and immediately starts a fresh stable scan at the unchanged scroll position. A completed slot is suppressed even if stale recognition still reports its pre-purchase target. Scanning continues until the viewport has a stable empty result. The completed-slot set is reset only after a confirmed refresh. Purchases never trigger an upward scroll, and row 4 has no special branch.

Refresh is allowed only when `spent + fixed_cost <= limit`. First entry, re-entry, strategy/network recovery, ambiguity, and retry/failure boundaries require a fresh stable Sky Stone parse. The strict gem/plus template is searched only within the full-width top-bar band, never the whole client. From the detected icon-relative start, vision examines a bounded corridor to the client edge and decodes only the first baseline-aligned contiguous digit run; a template-derived large gap ends the run before distant notification controls, while an unsafe component inside the run rejects the entire balance. Digit count is not preset. Both bands stay in baseline coordinates and use the same ROI projection/cache path as other recognition on non-reference clients. After an exact confirmed refresh, the resulting balance is trusted only while the engine remains in the same certain in-shop state; an ordinary next refresh reuses that value instead of immediately rereading the same three frames. The engine clicks refresh once, requires both the refresh-specific prompt and blue confirmation button to appear stably, then clicks refresh confirmation once. Internal spending increases only when the post-confirm balance is stably equal to `before - 3`. The unchanged old value remains pending until timeout; any other stable delta terminates with `refresh_balance_mismatch` and no internal count. Frames that already show the exact expected balance also accumulate the next top inventory's stability, but no inventory action is allowed until exact balance confirmation succeeds. A concurrent stable top result is consumed once by the next cycle; otherwise the original independent stable top scan runs unchanged. If the refresh exactly consumes the budget, the new top and bottom viewports are fully scanned before the next refresh check terminates the run.

The 180-second strategy recovery can leave the main screen in its UI-hidden standby state. After that wait only, the engine sends one ordinary guarded click to the calibrated client center `(1161,653)` before the normal stable main-shop recognition and entry sequence. The 5-second recoveries skip the wake click.

Only a fully scanned inventory produced by a confirmed refresh advances the no-target strategy; the initial inventory does not. An available mandatory Covenant Bookmark or Mystic Medal resets the strategy immediately, while Friendship Points and purchased-state classifications do not. Consecutive no-target batches are `(13,13,13,10)`. Recovery after the first batch is stable exit, checkpointed 5-second main-screen wait, and stable re-entry; after the second it uses the same sequence with a 180-second wait; after the third it uses a 5-second wait. Completing the final batch raises `refresh_strategy_exhausted`. F5 and exact window/client geometry are rechecked throughout every wait. The currency budget is checked before recovery, so a run that cannot afford the next refresh stops without an unnecessary wait or exit.

Purchase result polling accepts only an explicit success or an insufficient-purchase-currency warning stable for the configured consecutive-frame count. A non-warning frame resets warning stability. Timeout is ambiguous and terminates without retry or count changes.

## Ports

`ports.py` defines replaceable runtime-integrity, window, capture, client-coordinate input, hotkey, overlay, clock, and logger interfaces. Offline tests supply only fakes. The production WGC capture implementation is isolated in `wgc_capture.py` and loaded only inside the automation worker; window-message input is isolated in `background_windows.py`; OpenCV recognition and inventory-scroll measurement are isolated in `vision.py` and accept in-memory arrays only.

WGC validates positive `ContentSize` against the copied surface dimensions, then slices the valid top-left content before selecting a client-crop coordinate origin. Item/pool dimensions may include invisible borders while content matches DWM visible bounds; their inequality alone is not a capture failure. The existing crop maps valid content to DWM bounds or the outer window rectangle, or accepts client-sized content directly. Invalid/truncated content, unmappable geometry and client overflow still fail closed; engine window/display guards remain unchanged. Client output is contiguous, including the client-only path with surface padding.

Text logs include aggregate `performance_stage` records for inventory scans, scrolling, balance reads/waits, and refresh execution. Each record reports total duration plus capture, vision, and non-reference ROI-normalization counts/times; no performance path persists screenshots or writes per-frame timing files.

## Penguin exchange

`automation/penguin.py` implements the separate 50-penguin batch flow. It inherits guarded preparation/input and network recovery from `AutomationEngine`, overriding execution, post-recovery capture and normal completion; it never enters shop scans, refresh strategies or balance verification. `AutomationSession.run_penguins` shares F5 registration and resource cleanup. `RuntimeSnapshot` stores the feature id and separate successful-batch count/limit.

Penguin capture calls the shared network handler, discards the interrupted frame after recovery and captures anew. A recovery generation counter resets stable observations in penguin waits and shared entry confirmation/rechecks, including instant recovery with zero elapsed delay. Penguin recognition deadlines and maximum-price settling use the shared active clock, which excludes network recovery time; the UI elapsed timer continues. Recovery temporarily shows `重连中`, restores the previous activity status and resumes the pending recognition, never replaying a purchase submission. If recovery leaves an unknown purchase outcome, the existing result timeout still stops the run.

`penguin_vision.py` validates the approved RGBA control assets. Every dialog needs max/cancel controls and the purchase-button body; the full 5100 template plus separately decoded yellow price digits authorize purchase. Only price-field pixels enter the digit reader. Existing digit shapes are reused with an independent yellow mask and confidence gate. Unknown prices are distinct from a positively decoded non-5100 price. A lower price after max must survive the settling window before normal completion.

`ui/pages/penguin.py` owns the purchase-limit input, read-only estimated leaf cost (`limit * 5100`, thousands-separated or `—` for invalid input), start button and F5 hint. The estimate reads no game balance. `StatsOverlay` switches between shop statistics and the four penguin lines while retaining drag/collapse. Reconfiguring hides stale labels before deferred Qt deletion. Returning to the function center after a stop hides the overlay; opening a settings page keeps it hidden until the next run positions it. Only one task can run at once.

Main-screen shop and sanctuary entry now share `AutomationEngine._enter_with_retry` and its destination/main recheck helper. A confirmed main-screen observation is passed directly to the click; timeout rechecks produce fresh observations before authorizing a retry. Both entries permit at most three clicks, preserve the shop's destination-first recheck behavior, and retain guarded input/F5. Only the main-screen sanctuary icon skips its former duplicate recognition. After sanctuary arrival, the forest entry retains its independent stable pre-click recognition. Purchase submissions do not use this helper.

The shared entry helper accepts an optional timeout override. Sanctuary passes 10,000 ms for both post-click arrival and subsequent destination/main recheck to tolerate its transition animation; shop retains its configured 5,000 ms. Successful stable detection continues immediately. Neither an unrecognized transition nor timeout alone permits another click; only stable main-screen evidence does. F5 interrupts both waits.

Function-center shop and penguin backgrounds both use `_ModuleCard._draw_cover_pixmap`: aspect-preserving cover scaling, centered cropping, `_IMAGE_ZOOM=1.0`, smooth interpolation and a scaled-size cache. The approved penguin v6 image is `assets/ui/penguin-card-background.png`; the shared card also supplies rounded clipping and the left-side title gradient. There is no penguin-specific scaling override.
